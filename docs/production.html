H100 Production Blueprint

How to take the grounded RAG chatbot (V4.3: hybrid retrieval, calibrated relevance gate, evidence by sentence ID, verification cascade) from one laptop to a multi-GPU H100 cluster. The pipeline and its safety rules stay the same; the models, serving layer and data layer change.

Reference cluster: 2 nodes × 8 H100 80 GB SXM (16 GPUs, NVLink inside a node). Where this page gives speeds, they are planning estimates to confirm with a load test, and the calculators let you change every assumption.

The principleOn the laptop every model call was expensive, so the design minimized them. On H100, spend the extra capacity on accuracy: a stronger answer model, an independent checker, more evidence per question, and image understanding at ingest.

Cluster architecture

  • The RAG API is stateless and runs on CPU. It runs today's ask() pipeline, rewritten as async, and only coordinates: every heavy step is a network call to a model pool or the database. Scale it on request rate.
  • Each model is its own pool of replicas behind a load balancer: vLLM for chat models, Hugging Face Text Embeddings Inference (TEI) for the embedder and reranker. Pools scale independently on queue depth.
  • Ingestion is a separate path driven by a queue, so a 10 GB upload never competes with users for answer GPUs.

  • Answer replicas are spread over both nodes, so losing a node halves capacity instead of causing an outage.
  • MIG splits one H100 into up to 7 isolated slices. The query-time embedder, reranker and small rewrite model don't need a whole GPU each.
  • Ingest GPUs scale to zero when the queue is empty and are borrowed for answer replicas at peak.
  • If one model needs more than one GPU (Llama 70B, or Qwen3-235B for a premium tier), keep its tensor-parallel group inside one node. NVLink between those GPUs is far faster than the network between nodes.

Memory planner

A replica's GPU memory holds the weights plus the KV cache, the attention state for every token of every active request. The KV cache decides how many questions one replica can serve at once.

Plan a replica · architecture values are approximate, from public model configs

KV bytes per token = 2 (key and value) × layers × KV heads × head dim × KV bytes. Free KV memory = 80 GB × utilization − weights ÷ GPUs − ~4 GB runtime overhead, summed over the replica's GPUs. Concurrent requests = free KV ÷ (KV per token × tokens per request). Ignores prefix sharing, which raises real concurrency for this workload (every request shares the same system prompts).

Latency budget

A checked answer is still a chain of model calls. On H100 each call is fast, but the chain adds up, so this budget decides whether to stream drafts, which calls can run in parallel, and where a faster model pays off.

Estimate one answer · defaults are planning assumptions; replace them with load-test numbers

Evidence = evidence prompt ÷ reading speed + 30 ID tokens ÷ writing speed. Answer = ~800 quote tokens ÷ reading + answer ÷ writing. Check = ~1,000 tokens ÷ reading + ~15 tokens per sentence ÷ checker writing. Rewrite = small model, ~150 ms. Laptop today: 8–16 s per new question, measured.

Where the time goes on H100Writing the answer dominates once reading is fast. Stream the draft immediately (already built), and run the fact check sentence by sentence while the answer is still being written. The answer then looks ready about when its last word appears.

Data layer

  • Vectors: stay on Postgres + pgvector up to roughly 10M chunks: store halfvec (16-bit), keep the HNSW index in RAM, one primary plus read replicas. Beyond about 50M chunks, move vectors to a dedicated engine (Qdrant or Milvus) with quantization and sharding. The decision is already recorded in docs/decisions.md.
  • Keyword search: replace the OR-ed ts_rank_cd query, which slows down on common words at scale, with a BM25 index: ParadeDB pg_search inside Postgres, or OpenSearch. With BGE-M3, its sparse vectors can do this job instead.
  • Raw files: S3-compatible object storage; Postgres keeps only text, metadata and vectors.
  • Backups and disaster recovery: point-in-time recovery for Postgres; vectors can always be rebuilt from object storage plus the embedding model, so a model's vectors are reproducible.

  • Kubernetes with the NVIDIA GPU Operator (drivers, MIG, DCGM metrics). Model servers autoscale on queue depth (KEDA); the API autoscales on request rate.
  • LLM tracing (for example Langfuse) records each answer's evidence IDs, verdicts and removed sentences, so a user's report can be replayed exactly.
  • Model weights are pinned by version and hash and pulled from an internal registry, not the internet, so every node runs the same model and a release is reproducible.
  • Canary releases: a new model or prompt first serves a small share of traffic on the spare GPUs, with automatic rollback if the evaluation gate or the SLOs regress.

Rollout plan

  1. Grow the evaluation set. 47 questions → 300+, written from real users' questions, with a held-out split never used for tuning. Add multi-part and multi-turn cases, since they are today's weakest area.
    Exit: the set covers every document type and failure mode in docs/hallucination.md.
  2. Abstract the model client. Make rag/ollama.py an interface with Ollama and OpenAI-compatible backends, and switch the pipeline to async. Laptop mode keeps working.
    Exit: all unit tests and the full evaluation pass unchanged on the laptop.
  3. Single-node staging (1 × 8 H100). vLLM + TEI, today's models first, so infrastructure problems aren't mixed up with model changes.
    Exit: same evaluation score; latency and throughput measured; the calculators above filled in with real numbers.
  4. Model upgrades, one at a time. Embedder and reranker (re-ingest, recalibrate), then the answer model, then the independent checker. Run the evaluation and calibration after each.
    Exit: each swap keeps or improves the score, with no rise in wrongly refused real questions.
  5. Cluster, security, scale. Second node, autoscaling, login and row-level security, BM25, load test at 2× expected peak, failover drill (kill a node mid-test).
    Exit: SLOs hold at 2× peak and through a node loss.
  6. Production with guardrails. Canary releases, evaluation as a CI gate, weekly recalibration on new labelled questions, on-call runbooks.
    Exit: two weeks inside SLO, then widen access.
