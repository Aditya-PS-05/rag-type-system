RAG Algorithm Field Guide

Every algorithm in the local RAG chatbot, in the order a question meets it, with the exact parameters from the code (V4.3). Each entry explains the idea, the steps, why it was chosen, and how it can fail. The demos run the same logic as the Python, ported to the page.

The system answers questions about 35 Wikipedia articles, 20 arXiv papers and 100 NASA images (155 documents, 3,537 chunks) using qwen3:4b-instruct and nomic-embed-text on a laptop.

Ingest

Loading and cleaning

rag/loaders.py · clean_wikipedia, clean_pdf_page, load_image, load_manifest

All three document types become plain text with a title and a source link, so one retrieval pipeline serves them all. Every downstream step reads data/raw/manifest.jsonl, one line per file.

  1. Wikipedia text: cut everything from "See also", "References", "Notes", "External links" onwards; strip heading markup.
  2. PDF: extract text per page with pypdf; join hyphenated words split across lines ("observa-\ntion" → "observation") and soft line wraps; strip control characters (Postgres rejects the NUL byte). The arXiv abstract from the manifest becomes page 0.
  3. Image: a text document built from metadata: Image: title, date, keywords and NASA's description. The pixels are never read.
WhyReference sections are dense with names and dates that match many questions but answer none. Images need text to be searchable, and NASA's captions are detailed.
Fails whenPDF tables and figures become run-on text, and an image with a poor caption is effectively invisible.

Incremental ingest by content hash

rag/store.py · content_hash, is_current, upsert_document · rag/ingest.py

Each document's text sections are hashed (SHA-256). Before embedding, ingest asks the database whether a row exists with the same team, path, hash and embedding model. If it does, the document is skipped; if not, the old rows are deleted and the new chunks inserted in one transaction.

skip(doc) ⇔ ∃ row: team = T ∧ path = p ∧ content_hash = sha256(sections) ∧ embed_model = M
WhyEmbedding is the slowest part of ingest (~40 chunks/s on the laptop). Re-running after adding a few files costs seconds, not minutes. Including the model name means switching embedders re-embeds everything automatically.
Fails whenChunking parameters change but the text doesn't: the hash is the same, so old chunks stay. Use --force.

Chunking: greedy paragraph packing with overlap

rag/chunking.py · chunk_text(text, max_chars=1200, overlap=200)

  1. Split the text into paragraphs on blank lines and collapse whitespace inside each.
  2. A paragraph longer than max_chars is split on sentence ends; a single sentence still too long is cut every max_chars characters.
  3. Pack paragraphs greedily into a buffer until the next one would exceed max_chars; then emit the chunk.
  4. Start the next chunk with the last ~overlap characters of the previous one (cut forward to a word boundary), if it still fits.
Try it · same algorithm as chunk_text

Highlighted text is the overlap repeated from the previous chunk. The real setting is 1,200 / 200; the demo uses smaller numbers so the effect is visible on a short text.

WhyParagraphs are natural units of meaning, so packing them keeps facts whole. 1,200 characters fits comfortably in the embedder and the reranker. Overlap keeps a fact that sits on a boundary findable from either side.
Fails whenA pronoun's subject is in the previous chunk ("It launched in 1977"). That is what neighbour expansion fixes at query time.

Embeddings and cosine similarity

rag/ollama.py · embed_documents, embed_query · model nomic-embed-text, 768 dimensions

An embedding model maps text to a point in 768-dimensional space so that texts with similar meaning land close together. Closeness is measured by the angle between vectors:

cos(q, d) = (q · d) / (‖q‖ ‖d‖) pgvector distance q <=> d = 1 − cos(q, d)
  1. Each chunk is embedded as search_document: {title}\n{chunk}. Prepending the title gives every chunk its subject, even one that only says "it".
  2. Questions are embedded as search_query: {question}. nomic-embed-text was trained with these task prefixes; leaving them out measurably lowers retrieval quality.
  3. Documents are embedded in batches of 32; inputs over the model's context are truncated.
WhyOpen weights, 274 MB, fast on a laptop, 8k-token context, good retrieval quality for its size.
Fails whenExact identifiers matter ("PIXL", "GW150914"): embeddings blur rare tokens. That is why keyword search runs alongside.

Index

HNSW: approximate nearest-neighbour search

rag/store.py · CREATE INDEX … USING hnsw (embedding vector_cosine_ops) · search()

Comparing a question with every stored vector is exact but linear in corpus size. HNSW (Hierarchical Navigable Small World) builds a layered proximity graph instead and walks it greedily.

  1. Build: each vector is inserted at a random top layer (exponentially fewer nodes per higher layer) and linked to its m nearest neighbours on every layer it occupies (pgvector default m = 16, ef_construction = 64).
  2. Search: enter at the top layer, greedily move to whichever neighbour is closer to the query until no neighbour improves, then drop a layer and repeat. On the bottom layer keep a candidate list of size ef_search (default 40) and return the best k.
  3. Filtering: every query filters by team, embedding model and optionally document type. A plain HNSW scan returns the top 40 and then filters, which can leave fewer than k results. The code sets hnsw.iterative_scan = relaxed_order (pgvector 0.8), so the scan keeps going until enough rows pass the filter.
WhySearch cost grows roughly with log(n), so tens of millions of vectors stay in the tens of milliseconds while the graph fits in RAM. At 3,537 chunks the index is 14 MB.
Fails whenIt's approximate: a true nearest neighbour can be missed. That's harmless here because 30 candidates feed a reranker. At scale, the graph must fit in memory or latency jumps.

Full-text index: tsvector + GIN

rag/store.py · chunks.tsv = to_tsvector('english', title || ' ' || content) · GIN index

Postgres turns text into a tsvector: lowercased, stemmed lexemes with their positions, minus stop words. "The rovers landed" becomes 'land':3 'rover':2. A GIN (generalized inverted) index maps each lexeme to the chunks containing it, like the index at the back of a book.

WhyExact-term matching lives in the same database as the vectors, so there's no second search service to run. Including the title lets "Juno" match every chunk of the Juno article.
Fails whenEnglish stemming only; no typo tolerance ("Chandrayan" misses "Chandrayaan"). The vector side covers those cases.

Retrieve

Keyword search: OR query ranked by cover density

rag/store.py · keyword_search · plainto_tsquery → OR → ts_rank_cd · top 30

  1. plainto_tsquery('english', question) builds an AND query of the question's lexemes: 'pixl' & 'instrument' & 'persever'.
  2. The code rewrites every & to |, so a chunk matching any term qualifies. With AND, one word missing from a long question would discard the right chunk.
  3. Matches are ranked by ts_rank_cd (cover density): chunks where more query terms appear close together rank higher.
WhyOR maximizes recall; precision is the reranker's job.
Fails whenAt millions of chunks, common words ("launched") match a large share of rows and all of them get ranked. A BM25 index is the fix at that scale.

Reciprocal rank fusion

rag/retrieval.py · rrf_fuse · RRF_K = 60 · fused pool cut to 24

Vector and keyword scores live on different scales (cosine 0–1 versus unbounded ts_rank_cd), so they can't be added. RRF ignores the scores and uses only each chunk's rank in each list:

RRF(d) = Σ over lists L containing d 1 / (k + rank_L(d)) k = 60

A chunk ranked high by either method scores well; a chunk ranked high by both scores best. The constant k damps the gap between rank 1 and rank 2, so one list can't dominate.

        Cross-encoder reranking

        rag/rerank.py · jinaai/jina-reranker-v1-turbo-en (ONNX, fastembed) · pool 24 → top 8 · score = sigmoid(logit)

        The embedding model is a bi-encoder: question and chunk are encoded separately, then compared. A cross-encoder reads them together, so every question word can attend to every chunk word. It is far more accurate and far slower, so it only sees the 24 fused candidates.

        1. For each candidate, score the pair (question, title + "\n" + chunk).
        2. Map the raw logit to 0–1 with the logistic function: s = 1 / (1 + e^(−logit)).
        3. Sort by s and keep the top 8. That score becomes the chunk's relevance and drives the gate.
        Whyjina turbo gave the same top results as bge-reranker-v2-m3 in testing at 0.7 s instead of 6.3 s on CPU. Its scores also separate real questions from off-topic ones far better than cosine did.
        Fails whenScores are relative, not probabilities. A question that is on-topic but unanswerable can still score 0.87, so the gate can't be the only defence.

        Image intent

        rag/retrieval.py · VISUAL_INTENT · _ensure_images · IMAGES_PER_VISUAL_QUERY = 3

        If the question matches \b(images|image of|pictures?|photos?|photographs?|show me|looks? like)\b, ten more candidates are fetched from images only and added to the rerank pool, and the final list puts the best 3 images first. "Image" on its own isn't a trigger, because papers say "we image the surface".

        Neighbour expansion

        rag/retrieval.py · with_neighbors · NEIGHBOR_CHARS = 250 · store.chunk_neighbors

        1. For each text or PDF hit, fetch the chunks just before and after it in the same document (one query for all hits).
        2. Skip a neighbour that is itself one of the hits; the model already reads it as its own source.
        3. Remove the overlap repeated from chunking, then add up to 250 characters of the previous chunk's end and the next chunk's start, cut at word boundaries.
        WhyChunks often start with "It…" or "The rover…". A little surrounding text restores the subject. Skipping duplicate neighbours and trimming 400 → 250 characters cut the evidence prompt by 24%, with no expected answer lost.
        Fails whenThe subject is more than 250 characters away; the ±1-sentence evidence context partly covers this.

        Gate

        Relevance gate

        rag/qa.py · ask() · refuse if max(score of top 8) < threshold · threshold from calibration.json

        Before any language-model call, look at the best reranker score. If even the best chunk is below the threshold, answer "I don't know based on the available documents." The model is never asked, so it has no chance to answer from its own memory.

        Try it · the real scores of all 47 evaluation questions

        Hover a dot to see its question. Hollow dots are the held-out test split.

        WhyOff-topic questions score 0.01–0.11 while every answerable one scores at least 0.46. The gate removes them for free and with certainty.
        Fails whenTraps that are on-topic but not answered by the documents (Gagarin's breakfast 0.69, NASA tweets 0.79, a cost in euros 0.87) overlap real questions. They pass the gate and are stopped later by evidence selection.

        Threshold calibration

        rag/calibrate.py · split_of, choose_threshold, fingerprint, apply · position = 0.25

        1. Score: run only retrieval (no answer generation) for every evaluation question and record the best score. About 25 s.
        2. Split: assign each question to tune or test by a stable hash: int(sha1(q)[:8], 16) mod 100 < 30 → test.
        3. Choose on the tune split only:
          floor = lowest answerable score (after allowing 1 − min_recall to fall below) ceiling = highest trap score below floor t = ceiling + (floor − ceiling) × position position = 0.25
        4. Report on the test split: answerable questions wrongly refused, traps stopped.
        5. Fingerprint: save t with the team, embedding model, scorer and a corpus digest (SHA-256 over every document's path, content hash and chunk count). At start-up, chat, eval and the web app recompute it and print STALE if anything changed.

        Position 0.25 leans the threshold towards the traps because the two errors aren't equal: a refused real question is lost, while a trap that passes still faces evidence selection and the fact check. The midpoint rule (0.501) wrongly refused a held-out question at 0.46; that's what changed the rule, so the case no longer counts as a clean test.

        Answer

        Follow-up detection and rewriting

        rag/qa.py · needs_rewrite, FOLLOW_UP, rewrite_question · last 4 turns

        Search needs a self-contained question: "When was it launched?" retrieves nothing useful. If there is chat history and the question could refer back, one JSON-constrained LLM call rewrites it ("When was Voyager 1 launched?"). The history is used only for that; it is never a source of facts.

        The check is a regular expression for pronouns and demonstratives (it, its, they, this, those, there, same, other…), definite references (the rover, the mission, the telescope…), openers (and…, what about…), or a question of at most two words.

        Try it · same pattern as needs_rewrite
        WhyThe rewrite costs about 1 s; most questions in a conversation are already standalone.
        Fails whenAn elliptical follow-up uses none of these words ("How many days before the final plunge was the aurora image taken?"). It still worked in testing because its own words were specific enough to find the right image.

        Evidence selection by sentence ID

        rag/grounding.py · number_sentences, quotes_from_ids · rag/qa.py · select_evidence · top 6 sources, ≤ 10 IDs, ±1 sentence

        1. Split each of the top 6 sources into sentences and number them source.sentence (2.5 = source 2, sentence 5), up to 40 per source. An image is a single unit, clipped to 600 characters at a sentence end.
        2. The model sees the numbered sentences and the question and returns only IDs, as JSON with at most 10 items.
        3. Code turns IDs into quotes: each ID also brings the sentence before and after it; consecutive sentences of one source merge into one quote. An ID that doesn't exist is kept as an unverified quote, shown but never used.
        4. No valid ID → refuse. Otherwise only these quotes go to the answer step.

        WhyQuotes are exact source text by construction, since the model can't paraphrase an ID. IDs cost about 15 output tokens; copying quotes cost about 150 (6–11 s) and needed fuzzy matching.
        Fails whenThe model picks the wrong sentences; the answer then lacks the fact and may refuse. This step is also the main cost: reading the ~2,000-token numbered prompt takes 3.5–5 s.

        Schema-constrained JSON decoding

        rag/ollama.py · chat_json(messages, schema) → Ollama "format": schema

        The rewrite, evidence and fact-check calls pass a JSON Schema. The model runtime turns it into a grammar and masks every token that would break it, so the output always parses. maxItems: 10 on the evidence IDs is enforced the same way: one question had produced 74 IDs (15 s of output) before the limit.

        Answering rules

        rag/qa.py · ANSWER_PROMPT · temperature 0 · at most 400 tokens · num_ctx 8192

        • Use only the quotes; end every factual sentence with its citations [n].
        • One fact per sentence; no conclusions or comparisons the quotes don't state.
        • Answer every part of the question; if part is missing, answer the rest and add one sentence naming what is missing. Refuse only when nothing is answerable.
        • At most 4 sentences (8 for lists or details). Describe images in prose and say they can be viewed.

        Temperature 0 makes the model pick the most likely token every time, so answers are repeatable for the same input.

        Verify

        Claim splitting and citation check

        rag/grounding.py · split_claims, check_citations

        1. Split the answer at sentence ends (a period followed by a capital, quote or bracket) and line breaks; a trailing [1][2] on its own joins the sentence before it.
        2. Drop fragments under 25 characters and headings ending in ":".
        3. For each sentence, read its citations. No citation → issue no citation; citing a source with no verified quote → issue cites unquoted source. A sentence saying what the documents don't contain ("The documents do not say…") is recorded as a gap statement and isn't treated as a claim.

        Verification cascade

        rag/grounding.py · copies_evidence, closest_source, verify_claims, add_citations, remove_claims

        Each sentence goes down a cascade. Cheap, certain checks come first; the language-model judge sees only what's left.

        StepRuleOutcome
        Gap statementmatches "documents/sources do not say…"kept, no check
        Uncited sentenceargmax over quotes of |words(sentence) ∩ words(quote)|given that quote's citation, then judged
        Exact excerptnormalize(sentence) ⊂ normalize(cited quotes)supported, no LLM call
        LLM judgeone batched call, all remaining sentencessupported / unsupported + reason
        No verdict returnedmissing from the judge's JSONtreated as unsupported
        Removedelete unsupported sentencesnone left → refusal
        Add citationsauto-cited sentences that survived[n] inserted before the final period

        Normalization lowercases, collapses spaces, removes quote marks, brackets and citations. Only a contiguous excerpt counts: "entered interstellar space on August 25, 2013" is not an excerpt of a source saying 2012, even though every word appears in it. Word overlap ignores stop words (the, of, in, was…).

        The judge's rules: paraphrases, synonyms, alternative names and simple inferences (comparing two dates, counting) are supported. A name, number, date, place or event missing from the cited quotes, or contradicting them ("announced" read as "happened"), is not.

        WhyDeleting a wrong sentence protects the reader better than a warning under it. Batching makes the check one call (1–4 s) instead of one per sentence.
        Fails whenThe judge is the same 4B model that wrote the answer, so their errors are correlated. It also rejects whole sentences: a correct fact joined to an unsupported conclusion is lost, which is why the answer prompt asks for one fact per sentence.

        Refusal handling

        rag/grounding.py · is_refusal, without_refusal_sentences · rag/qa.py · ask()

        An answer counts as a refusal only when the refusal sentence is the whole answer. If the model mixes it into other text, that sentence is dropped and everything else goes through the full verification cascade.

        Bug this closedThe first version treated any answer containing "I don't know based on the available documents" as a refusal, which skipped the fact check. A wrong claim ("Cassini was deorbited into Jupiter's atmosphere") got through that way before the fix.

        Latency mechanics

        docs/performance.md · OLLAMA_KEEP_ALIVE = 30m · Ollama prompt cache

        time(call) ≈ prompt_tokens / 600 + output_tokens / 40 seconds, qwen3:4b on an M5 laptop
        • Reading dominates: the evidence prompt is ~2,000 tokens (3.5 s) and its output ~30 tokens (0.8 s). Shrinking input (top 6 sources, deduplicated, 250-character neighbours) saved more than any other change.
        • Prompt cache: Ollama reuses the processed start of a recent identical prompt, so a repeated question reads almost instantly. Always benchmark with new questions.
        • Keep-alive: every request asks Ollama to keep the models loaded for 30 minutes, and the web app loads them at start; a cold load cost about 5 s.
        • Perceived latency: in strict mode the web app streams the draft answer, then replaces it with the checked text. Text appears after about 5 s of an 8–16 s answer.
